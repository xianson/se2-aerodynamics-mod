**Game version:** SE2 4.0.0.3151 (re-checked 2026-10-19 for the 4.0 port; `C:\aero\decompiled\SE2_VERSION.txt` - the 2.4 decompiles are `C:\aero\decompiled-2.4.0.95` and `D:\aero\decompiled-2.4.0.77`). **Written:** 2026-10-03 for 2.4.0.77 (moved here from `D:\aero\docs\` the same day).

**Companion document:** the Orbital Mod's `docs/REFLECTION_AND_WHITELIST.md` holds the Orbital inventory, Orbital's calls into this mod (its §3.10), and the **shared** sections: how the mod compiler gates code (its §2), the combined assembly ask to Keen (its §5.0) and the general risks (its §6). This file covers only the Aero mod's own reflection.

**Keep current:** every new or changed reflection use in Aero goes into this file in the same change; a change to a member other mods reach (`AeroApi`, `AeroEntryFx`) also goes into Orbital's §3.10.

## 1. Summary

- About 40 source lines call a reflection API, in 5 files. Grep also hits `AeroWork.cs` and `DampedShadowedDragModel.cs`, but those are plain delegate `.Invoke`.
- 12 distinct engine members are reflected, in VRage.Game.Client (particle effects, the grid's render parent), VRage.Render (effect parameters, spot light, render roots), VRage.DCS (protected `Component.SetData<T>`, internal `EntityCompositeDefinition.Assign`), VRage.Core.Game (private `PrefabDefinition._entity`) and Game2.Simulation (private block `_definition` fields, `CubeBlockComponent.Definition` to dodge a CS0012).
- **Shipped features that live on reflection:** re-entry plasma and the flight field (sparks, vapour, tip trails, spot light), definition injection of the aero components, thrust torque (thruster / gyro definitions), engine control overrides.
- **The Aero public API (`AeroApi`, `docs/API.md`) has no engine reflection.** Other mods reach it by reflection on their side; Orbital's calls are inventoried in Orbital's §3.10.
- **Why reflection at all:** see Orbital's §2. In short, mod scripts compile only against VRage.Core, VRage.Library, VRage.DCS, VRage.Core.Game, Game2.Simulation, Game2.Client and VRage.Physics (+ CoreLib); the namespace whitelist allows `System.Reflection`; private, protected and internal members need reflection regardless.

### 5.13 Control-panel settings for mod blocks (2026-10-13: the 3x3x1 control surface's terminal; also the thruster's and Orbital's radar)
What a mod needs to give its block a terminal panel that works like a vanilla one, most important first. Today it needs
four workarounds (§3.9: DetailModelPairing, ModDetailTypeInfo, and settings saved as text) and still works for the
host / single player only.
- **(A) Run the game's source generators on mod scripts**, or ship their output: `VRage.Library.Generator.dll`
  (`IAccessible` / `TypeInfoHolder`, `[Notify]`, serializers) and `VRage.DCS.Generator.dll` (`[SyncProperty]` signals,
  `[Init]` / `[Serializer]` object builders). This one request covers most of the rest:
  - a panel model's member list (we hand-build `GetTypeInfo()`: `ModDetailTypeInfo`);
  - `[Notify]` / `[Bind<Prop<...>>]` component-to-panel binding (we read the component in property getters; the panel does not refresh when something else changes it);
  - a mod component's own `[Serialize]` object builder, saved with the block - and readable when the mod is gone. Since 2.4.0.95 a mod's `[Serialize]` class compiles, but a world that names a mod type no longer loads once the mod is removed (the binary reader throws on the missing type), so a mod cannot use one safely. Since 2026-10-15 each block keeps its settings as one text key on the engine's `EntityNameSessionComponentObjectBuilder` in its own component slot (`Blocks/AeroBlockSave.cs`; before: text lines on a planet's carrier matched back by world position, `AeroSurfaceSaved`, still read for old saves). Asked: an engine-provided, removal-safe key / value builder for mod components, or a missing builder type read as "no data" instead of a load failure.
- **(R) VRage.Multiplayer as a mod reference, with `[Replicate]`, `[SyncFromClients]` and `[SyncProperty]` whitelisted.** Without them:
  - a client's edit never reaches the server, so mod panels are host / single player only;
  - a property can't become a toolbar action (`BlockDetailProviderIndexer.IsPropertyEligible` requires `[SyncFromClients]`), so there's no "toggle pitch" or "flaps 20" on the toolbar;
  - `EntityId` is unreachable (we use reflection in the DEV probe).
- **(R) System.ObjectModel as a mod reference.** `BlockDetailModel` derives from `ObservableObject`
  (`INotifyPropertyChanged` / `INotifyPropertyChanging`). Without the reference a mod can't pass its own model as `IAccessible`
  or read `ControlPanelListModel.Blocks` (`ObservableList`) without going through `object` or reflection.
- **(N) The control panel should not kill the game over an unpaired model.**
  `StreamedControlPanelSessionComponent.AttachBlockDetailModels` calls `IReplicationWorkarounds.TranslateLocalToRemote` on every
  model. For a mod model that isn't replicated, that lookup threw `KeyNotFoundException` and crashed the game (2026-10-04).
  Falling back to the object itself, which is what the game does with observable replication off, would remove our
  protected `ReplayContext` read (`DetailModelPairing`).
- **(N) Documented:** a `[BlockDetailProvider]` model is shown only with `[BlockDetailDisplayMode(DisplayMode.Controls)]`.
  Nothing says so, and none of our first three panels had it.
- **Without Keen:** what ships now (§3.9). Power and on/off need nothing: a block built on the vanilla
  `BasePowerableBlockBreakable` template gets `PowerableBlockComponent`, its toggle, its draw (`PowerableBlockDefinition.ConsumedResource`, kW)
  and `PowerableBlockDetailModel` from the game.

### 5.14 Retractable gear built on the vanilla wheel (2026-10-13, `Integration/AeroGearComponent.cs`; tested in game: 10 cycles clean)
The wheel is the vanilla suspension's own, always present. Retracting slides it up its suspension axis by moving the live
wheel constraint's limits (`IWheelConstraint.MinSuspensionLimit` / `MaxSuspensionLimit`, public). Deep in the well its
collision goes: its `EntityLayerData` is set to the "Ragdolls" layer, which meets no grid, voxel or character, and the
physics session re-filters the body on the change.
- **(P) `WheelCornerModuleComponent.WheelConstraint`, public.** We read the private field `_constraint` (one cached
  `FieldInfo`, §3.9) to reach the constraint. A public getter would remove the only reflection the gear uses.
- **(P) `WheelCornerModuleComponent.Suspension` (its `SuspensionInfo`), public** (2026-10-20, the wheel shocks): we read the
  private `_suspension` for the axis and stroke the strut works along.
- **(N) A suspension that takes an impact** (2026-10-20): the soft spring scales with the light wheel body's mass (factor x tau x
  m_wheel / dt^2: ~0.43 MN/m for a 200 kg 1 m wheel) and the hard limit takes the rest in one step; SE1's wheel contact response
  modifier (the impact spread) has no counterpart. A spring rate in N/m on `IWheelConstraint`, or the modifier, and the mod's
  wheel shocks (a stopgap) can go.
- **(N) Spawning an entity with a rigid body from a mod.** Our first design removed the wheel when up and re-made it
  when down, by calling the corner module's own lifecycle hooks (`IInSceneListener.OnBeforeRemovedFromScene` /
  `IEntityBundleListener.OnBundleAddedToScene`, public). Removal works at runtime; the build does not. From a mod's
  job, `IEntitySpawner.SpawnEntity` of the wheel prefab fails in `HavokWorldHelper.AllocateBody` ("Data not found" -
  its `RigidBodyMassProperties`, written by the collider in `[Init]`, is not visible yet; data writes are buffered in a
  job). The vanilla build hook fails the same way. A supported way to spawn a physical entity from mod code - a
  deferred spawn, or a call that runs at the next sync point - would let gear (and any spawning mod) create bodies.
- **(N) A collision on / off for a body.** We borrow the "Ragdolls" layer as "collides with almost nothing". A real
  no-collision layer, or `IPhysics.SetBodyCollisionEnabled`, would not depend on another layer's interaction table.

## 6. Risks (Aero)

The general picture (private and internal members, boxed-struct mutation, `Activator.CreateInstance` on structs) is in Orbital's §6. Aero-specific:
- **Load-time injection** (`A/Injection/Injections.cs:40-45`): the `TryInvokeMethod` result for the internal `Assign` is ignored, and a missing `_entity` throws an NRE that is not caught.
- **Boxed `ParticleEffectUserParameters`** is mutated in place and passed on; `Activator.CreateInstance` gives it its defaults (FlightField.Render.cs).
- **Matching by name or shape:** `TrySpawnEffect` is matched by first-parameter type (FlightField.SpawnEffect); `GetMethod` by name (FlightField.Render.cs) throws `AmbiguousMatchException` if Keen adds an overload; `CreateSpotLightEntity` (FlightField.Render.cs) is filled by parameter name.
- **`MakeGenericMethod` every call:** `Component.SetData<T>` (EngineOverrides.cs), guarded against the `T[]` ban by `Unsafe.As<Array, object[]>`.
- **Per-frame reflection:** `SetParameters` / `UpdateTransform` during entry; the flight field's root `UpdateTransform` every frame.
- **Repeat-throw paths:** effects after `Fail` are still driven; `SetData` has no alive check (EngineOverrides.TrySetComponentData logs every time).
- **Silent failures:** `BlockComponentFactory` GUID (aero blocks get no component); `OffsetThrustJob` `_definition` (thrust torque inert after a single log line).
